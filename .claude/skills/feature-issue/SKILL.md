# Feature issues

Obvid's features and optimizations go through GitHub: issue → approval → branch → pull request → the user merges.
This skill fixes the format of each step. It covers these two kinds only:
- **Optimization** (label `performance`): the same output, less time or memory. Most of the backlog.
- **Feature** (label `enhancement`): something new an app can use or switch on.

## The AI line

Every issue, issue comment and pull request body written by AI starts with this line, exactly:

```markdown
> *This was generated by AI.*
```

Followed by one empty line. Never reword it, never drop it, never add it twice.

## Issue

Title: concrete, no prefix: the change and its effect (`NEON small blur: faster shadows for radii under 2.6 px`).
Label: `performance` or `enhancement`.

Body:

```markdown
> *This was generated by AI.*

## What and why
<What changes for an app that uses Obvid, and why it matters: the case, the numbers measured so far (device, what
was compared), the current behaviour. Two to five sentences.>

<Links to the code involved, as permalinks pinned to the commit below.>

## Outcome
- [ ] <A result an app sees after this lands, and the check that proves it, in one item.>
- [ ] <...>

## Scope
- In: <what this issue changes>
- Out: <what it leaves for later, and where that is tracked if it is>

Checked against `<short commit SHA of main>`.
```

The Outcome is the definition of done: the issue is done when every box is ticked. Each item is a result (which
shadows change, what gets faster and the target against Compose, what stays identical, which documented limit or to-do
goes away, the changelog entry) with its check (host or device tests, a benchmark against Compose with the device and
the sampling rule, quality loss as PSNR and max error for anything approximate). If an item turns out wrong during the
work, edit it in the issue and say why; never drop it silently. A possible negative result (no speedup, so nothing
changes) goes at the end of What and why.

The repo is public. Issues are read by people who know nothing of the working notes:
- No references to local files that are not in the repo (working docs, `results/`, plans, traces), no device serials,
  no local paths. Quote the numbers themselves.
- Write in ASD-STE100 Simplified Technical English (STE): one topic per sentence, at most 20 words in an
  instruction and 25 in a description, active voice, one instruction per sentence, one meaning per word, the README's
  vocabulary. Short lists, not walls of text. Never write "byte-identical"; write "identical".
- Code links: `https://github.com/desugar-64/obvid/blob/<full SHA>/<path>#L<a>-L<b>`, the SHA being `origin/main`.

## Filing

1. Draft the issue in the conversation. File nothing until the user approves the draft.
2. Write the body to a file in the scratchpad, then:
   ```sh
   ${GH:-gh} issue create --repo desugar-64/obvid --title "<title>" --label <performance|enhancement> --body-file <file>
   ```
3. Give the user the URL. Check the posted body starts with the AI line (`gh issue view <n> --json body`).

Several issues at once: draft them all, get one approval for the set, file them in the order shown.

## Work on an issue

- Discuss the plan in the conversation first (CLAUDE.md working rules). A plan that the user wants recorded goes in
  an issue comment, AI line first.
- Branch from an up-to-date `main`: `<issue number>-<short-slug>`, e.g. `12-neon-small-blur`.
- Commit only when the user asks. Commit subjects in the repo's style (`scope: what changed`).
- If the feature changes what users get, add its line under `## Unreleased` in `CHANGELOG.md`, with a link to the
  issue. Never edit the version: that is the `release` skill's job.

## Pull request

Open it when the user asks, after the branch is pushed:

```sh
${GH:-gh} pr create --repo desugar-64/obvid --base main --title "<title>" --body-file <file>
```

Body:

```markdown
> *This was generated by AI.*

## Change
<What changed and why, in a few sentences or bullets. Public API changes called out.>

## Validation
<The issue's Outcome, item by item, each with what ran and what it showed: host tests, device tests (device, Android
version, pass count), benchmarks against Compose (device, both orders when the effect is 3–15 %), quality loss for
anything approximate.>

Fixes #<issue number>
```

CI (`rust`, `android`) must pass. Tick the issue's Outcome boxes that the PR proves. The user merges (squash); Claude
never merges.

## Closing

- The issue closes when its pull request is merged: `Fixes #<n>` closes it. Only a PR that proves every Outcome item
  (for an optimization, a measured gain against Compose) and shows no bug or regression may carry it: the host and
  device test suites pass, and the benchmark cases the change can reach outside its own are not slower. A PR that
  proves only part of it says `Part of #<n>` instead.
- No gain (the optimization is not faster): nothing is merged. Comment the numbers on the issue (AI line first), then
  close it as not planned: `${GH:-gh} issue close <n> --reason "not planned"`.
